# `0001_init.sql` — baseline schema initialization

## Purpose

Documents the raw SQL baseline initialization script used to bootstrap each service's PostgreSQL schema in a fresh environment (local Docker Compose, or a newly provisioned database before Alembic's chain takes over) — distinct from and predating the per-service Alembic migration chains described in [`README.md`](README.md).

## What it does

For each service schema, `0001_init.sql`:

1. Creates the schema itself (`CREATE SCHEMA IF NOT EXISTS <service>`).
2. Creates required PostgreSQL extensions (`pgcrypto` for `digest()` used in audit hashing, `uuid-ossp` or native `uuid_generate_v7()` support).
3. Grants the service's application role least-privilege access: `SELECT/INSERT/UPDATE` on its own tables, explicitly **no** `DELETE` grant on append-only tables (`ledger_entries`, `audit_entries` — see [`../constraints/constraints-catalog.md`](../constraints/constraints-catalog.md)).
4. Creates the shared trigger functions referenced across schemas (`set_updated_at()` — see [`../functions/functions-catalog.md`](../functions/functions-catalog.md)).

## When this runs

- **Local development**: applied automatically by `docker compose up` via the Postgres image's `/docker-entrypoint-initdb.d/` convention (see [`../../infrastructure/postgres/init.sql.README.md`](../../infrastructure/postgres/init.sql.README.md)).
- **New environment provisioning**: applied once by the infrastructure provisioning pipeline before Alembic's `alembic upgrade head` runs for the first time in that environment.
- **Never re-run** against an environment that already has data — it is idempotent for schema/role creation (`IF NOT EXISTS` guards throughout) but is not a substitute for ongoing migrations.

## Relationship to Alembic

After `0001_init.sql` establishes the baseline, all further schema evolution goes through each service's Alembic chain exclusively — `0001_init.sql` is not updated for incremental changes; it exists once, as the floor the migration chain builds on.
